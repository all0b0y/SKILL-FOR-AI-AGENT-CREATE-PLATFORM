# Production AI Agent Best Practices — Checkable Rules

Compiled from primary sources (Anthropic, OpenAI, Google, Microsoft, AWS, Vercel, humanlayer, Karpathy-derived guidelines) for the `agent-forge` plugin phases: grill → architect → build → evals → ui.

Format: `- **ID** rule. — Source: [title](url) (company) — Check: verification method — Verified: 2026-10-01`

---

## grill

- **GR-01** Decide whether the task even needs an agent: check if a single LLM call, a retrieval-augmented call, or a deterministic workflow already satisfies the requirement before committing to an agentic loop. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: interview transcript/spec must record why the chosen complexity tier was picked over every simpler alternative (single call, RAG, workflow) — Verified: 2026-10-01
- **GR-02** Classify every candidate tool/action by risk (low/medium/high) based on reversibility, required permissions, and financial impact before architecture starts. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: grill output contains a tool-risk table with a risk tier per planned tool, non-empty for any workload with write/delete/pay tools — Verified: 2026-10-01
- **GR-03** Capture an explicit exit/stop condition for every planned run (max turns, specific structured output, error threshold) during the interview, not after building. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: architecture doc lists a concrete stop condition (step cap, schema match, timeout) for every agent/workflow node — Verified: 2026-10-01
- **GR-04** Ask explicitly which actions require human approval (irreversible, financial, destructive) and record them as a separate, named list before architecture. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: grill output has a dedicated "approval-required actions" list; any write/delete/pay tool from GR-02 must appear on it or carry an explicit justification for not requiring approval — Verified: 2026-10-01
- **GR-05** Enumerate every untrusted/external data source the agent will ingest (web pages, emails, uploaded files, tool outputs from third parties) — each is a prompt-injection attack surface. — Source: [Mitigating the risk of prompt injections in browser use](https://www.anthropic.com/news/prompt-injection-defenses) (Anthropic) — Check: spec contains an explicit "untrusted data sources" list that is cross-checked against BU-09's injection-point implementation — Verified: 2026-10-01
- **GR-06** Do not default to multi-agent: require a specific justification (parallelizable breadth-first subtasks, context exceeding one window, tool-count overload) before the architecture phase is allowed to introduce more than one agent. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic) / [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: any multi-agent design in the output spec cites one of the named justifications explicitly, not "for modularity" alone — Verified: 2026-10-01
- **GR-07** Fix a numeric cost/latency budget (max tokens per run, target p95 latency) during the interview, since agentic systems trade both for accuracy. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: spec has required numeric fields `max_tokens_per_run` and `target_latency_ms` — Verified: 2026-10-01
- **GR-08** Confirm the task has an available "ground truth" signal the agent can check against mid-run (tool result, test execution, structured API response); flag tasks without any such signal as poor agent fits. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: spec names at least one verifiable feedback source per planned agentic task; tasks with none are routed to a simpler workflow pattern instead — Verified: 2026-10-01
- **GR-09** Pin the baseline model to the strongest available model during interview/architecture; defer any cheaper-model substitution decision until after an eval suite exists. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: spec names an explicit baseline model and contains no model-downgrade decision prior to the evals phase — Verified: 2026-10-01

## architect

- **AR-01** Place the design on the complexity ladder — single augmented LLM call → prompt chaining → routing → parallelization → orchestrator-workers → evaluator-optimizer → autonomous agent — and justify skipping any lower rung. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: architecture doc maps the chosen pattern to this ladder with a one-line reason for not using the simpler rung below it — Verified: 2026-10-01
- **AR-02** Use predefined-code-path workflows for well-defined, repeatable tasks; reserve open-ended autonomous agents for tasks whose steps can't be predicted in advance. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: each capability in the architecture is tagged `workflow` or `agent` with a justification referencing step predictability — Verified: 2026-10-01
- **AR-03** Choose the orchestrator-workers pattern only when subtasks cannot be pre-defined (unlike static parallelization/sectioning); otherwise use fixed parallelization. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: if orchestrator-workers is chosen, the doc explains why a fixed subtask list (parallelization) was insufficient — Verified: 2026-10-01
- **AR-04** Budget for roughly 4x the token usage of a single chat turn for a single agent, and roughly 15x for a multi-agent system, and require the task's value to justify that multiplier. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic) — Check: cost model includes explicit multiplier fields (chat=1x, agent≈4x, multi-agent≈15x) with a stated dollar budget per task class — Verified: 2026-10-01
- **AR-05** Prefer the centralized "agent-as-tool" pattern (orchestrator stays in control, calls specialists as tools) over decentralized "handoff" (agent permanently transfers control) unless the use case genuinely needs decentralized ownership. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: architecture doc states handoff vs agent-as-tool per multi-agent boundary with the reason for that choice — Verified: 2026-10-01
- **AR-06** Split a single agent into multiple agents only after evals show it fails to follow complex instructions or consistently selects the wrong tool — not preemptively. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: any multi-agent split cites a specific eval failure mode (instruction-following failure or tool mis-selection rate) that justified it — Verified: 2026-10-01
- **AR-07** Give every agent/subagent a single, narrow responsibility; an agent whose prompt covers multiple unrelated domains should be split so each agent produces focused, non-generic output. — Source: [Multi-Agent Portfolio Collaboration with OpenAI Agents SDK](https://developers.openai.com/cookbook/examples/agents_sdk/multi-agent-portfolio-collaboration/multi_agent_portfolio_collaboration/) (OpenAI) — Check: each agent's system prompt/spec entry maps to exactly one named responsibility in the architecture doc; multi-domain prompts are flagged for splitting — Verified: 2026-10-01
- **AR-08** Give each agent its own narrowly scoped toolset; never share a tool across agents operating in different trust/data-sensitivity domains. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: tool-assignment matrix shows no tool shared across agents flagged with different data-sensitivity domains — Verified: 2026-10-01
- **AR-09** Decide explicitly whether subagents execute synchronously (lead blocks until completion) or asynchronously, and document the resulting bottleneck/coordination tradeoff rather than assuming free concurrency. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic) — Check: architecture doc states the sync/async execution model for subagents and the known tradeoff it accepts — Verified: 2026-10-01
- **AR-10** Namespace tools by service and resource (`<service>_<resource>_<verb>`) whenever tools from more than one service or MCP server share the agent, to prevent confusion between overlapping tools. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: `check-tools` rejects an unprefixed tool name when the registry holds tools from more than one service/MCP server — Verified: 2026-10-01
- **AR-11** Route easy/common queries to small, cheap models and hard/unusual queries to frontier models per-step, rather than hardcoding one model for the whole system. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: architecture/config has a per-agent or per-route model field, not a single global model constant — Verified: 2026-10-01
- **AR-12** Persist full agent run state (messages, step index, tool results) in Postgres from day one so a crashed worker resumes mid-run instead of restarting from step 0. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic); [12-Factor Agents](https://github.com/humanlayer/12-factor-agents) (humanlayer) — Check: a `runs`/`run_steps` table stores enough state to resume; an integration test kills the worker mid-run and asserts it resumes from the last completed step, not the start — Verified: 2026-10-01
- **AR-13** Model each run step as a stateless reducer — `(prior_state, event) -> (new_state, next_action)` — so runs can be paused, serialized, and resumed by any process. — Source: [12-Factor Agents](https://github.com/humanlayer/12-factor-agents) (humanlayer) — Check: the run executor keeps no in-memory-only state that is not also written to persisted run state after every step — Verified: 2026-10-01
- **AR-14** Design every side-effecting tool/action handler to be idempotent via an idempotency key per run-step, since durable execution and model retries will replay steps. — Source: [12-Factor Agents](https://github.com/humanlayer/12-factor-agents) (humanlayer); [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — retry logic and checkpoints) — Check: every side-effecting tool call is keyed by `(run_id, step_id)`, and replaying the same key short-circuits instead of double-executing (covered by an automated test) — Verified: 2026-10-01
- **AR-15** Plan OpenTelemetry-style span tracing (agent, generation, tool-call, handoff, guardrail spans) stored durably in Postgres, not only in an external vendor dashboard. — Source: [Tracing — OpenAI Agents SDK](https://openai.github.io/openai-agents-python/tracing) (OpenAI) — Check: trace schema has distinct span types for agent/generation/tool/handoff/guardrail with `parent_id` links forming a tree per `run_id` — Verified: 2026-10-01
- **AR-16** Make maximum-turn / maximum-tool-call a required, finite run parameter at architecture time — "reaching a maximum number of turns" must be a designed exit condition, not an afterthought. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: run-config schema requires a finite `max_steps`/`max_turns` integer; no "unlimited" value is accepted in production config validation — Verified: 2026-10-01
- **AR-17** Run agent work through a durable queue (claim/lock with persisted status) rather than an in-memory/ephemeral one, so runs survive process restarts and deploys. (agent-forge implements this with pg-boss on Postgres — a stack decision, not part of the cited source.) — Source: [AWS Well-Architected Generative AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens/generative-ai-lens.html) (AWS — Reliability pillar: "handle failures gracefully... version artifacts... verify completion of distributed computation tasks") — Check: queue table has a `status` enum and a row-claim mechanism verified not to double-process a row under concurrent workers — Verified: 2026-10-01
- **AR-18** Plan rolling/rainbow worker deployments so in-flight agent runs on the old code version are drained, not hard-killed, by a deploy. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic) — Check: deploy pipeline keeps the old worker version draining in-flight runs for a grace period instead of terminating it on deploy — Verified: 2026-10-01

## build

- **BU-01** Implement a minimal, readable agent loop before adopting a heavy framework; if a framework is used, the team must be able to explain what it does under the hood. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: a reviewer can trace the run loop end-to-end in the codebase (or the AI SDK `ToolLoopAgent`) without opening framework internals — Verified: 2026-10-01
- **BU-02** Build fewer, more consolidated tools instead of thin 1:1 wrappers around every API endpoint; combine multi-step operations agents commonly chain into one tool. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: no two tools exist whose descriptions differ only by which of several chained API calls they wrap; tool count tracks distinct user intents, not raw API surface — Verified: 2026-10-01
- **BU-03** Name tool parameters unambiguously (`user_id` not `user`) and give every tool a singular, non-overlapping purpose. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: a schema linter flags generic parameter names (`id`, `data`, `value`) lacking a type-qualifying prefix, and flags tool-description pairs with high textual overlap — Verified: 2026-10-01
- **BU-04** Return token-efficient, high-signal tool responses: paginate/filter/truncate large outputs with sensible default caps, and expose human-readable fields (`name`, not only raw UUIDs). — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic — Claude Code's 25k-token default cap) — Check: every tool response enforces a max-length/token cap in code, and every returned object exposes a human-readable label alongside any machine ID — Verified: 2026-10-01
- **BU-05** Make tool error messages actionable and specific (what went wrong, what to change) instead of opaque error codes or raw tracebacks. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: tool error schema requires a human-readable corrective `message`; raw stack traces are never the primary error payload — Verified: 2026-10-01
- **BU-06** Expose a `response_format` (concise/detailed) verbosity control on data-heavy tools so the agent can request a summary or full detail as needed. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: any tool returning more than ~500 tokens by default exposes a verbosity parameter with a concise default — Verified: 2026-10-01
- **BU-07** Use just-in-time retrieval (query/search on demand) for large or stale data instead of dumping full datasets into the system prompt; load upfront only small, stable, universally-needed context. — Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (Anthropic) — Check: any data source above a size threshold (e.g. >2k tokens) is fetched via a retrieval tool call at run time, never concatenated into the static system prompt — Verified: 2026-10-01
- **BU-08** Implement context compaction for long-running agents: summarize completed work phases into external memory (DB/files) before continuing, and retrieve that memory instead of carrying full history forever. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — "long-horizon conversation management") — Check: the run executor triggers compaction past a token-count threshold, writing a summary record and pruning older messages, verified by a test that exceeds the threshold — Verified: 2026-10-01
- **BU-09** Pass untrusted external content (web pages, emails, tool outputs, uploads) through user-role messages inside a clearly delimited/tagged block; never splice it into system/developer instructions. — Source: [Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety) (OpenAI — "developer messages take precedence... pass untrusted inputs through user messages"); [Defending Against Indirect Prompt Injection Attacks With Spotlighting](https://arxiv.org/abs/2403.14720) (Microsoft Research — datamarking/delimiting) — Check: codebase has one designated injection point wrapping untrusted content in a consistent delimiter/tag (e.g. `<untrusted_data>`), and no raw string-concat of fetched content into the system-prompt builder — Verified: 2026-10-01
- **BU-10** Apply least-privilege scoping to every tool/credential; no tool should have broader read/write/delete access than its specific task requires, and agents that ingest untrusted data should not simultaneously hold high-privilege write tools. — Source: [Taxonomy of Failure Modes in Agentic AI Systems v2.0](https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/final/en-us/microsoft-brand/documents/Taxonomy-of-Failure-Mode-in-Agentic-AI-Systems-Whitepaper.pdf) (Microsoft — "excessive agency", "incorrect permissions"); [AWS Well-Architected Generative AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens/generative-ai-lens.html) (AWS — Security pillar: "mitigate risks of harmful outputs and excessive agency") — Check: a permission audit confirms each tool's credentials are scoped to the minimum resource it touches; any tool that both reads untrusted content and can write/delete is flagged for review — Verified: 2026-10-01
- **BU-11** Require explicit human approval before executing high-risk tool calls (irreversible, financial, destructive), implemented as a pause-and-resume step that halts execution until a decision is recorded. — Source: [Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) (OpenAI) — Check: every tool tagged high-risk in GR-02's risk registry has a matching approval gate that halts the run and persists resumable state until approved/rejected — Verified: 2026-10-01
- **BU-12** Implement guardrails as layered, independent checks (deterministic rules/regex + model-based classifier + moderation) instead of relying on a single LLM call to self-police input and output. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI — "layered defense mechanism... combine LLM-based guardrails, rules-based guardrails... and the moderation API") — Check: the guardrail pipeline has at least 2 independently implemented check types (one deterministic, one model-based) gating both input and output — Verified: 2026-10-01
- **BU-13** Run guardrails on every turn of a multi-turn run, not only on the first user message, since malicious content can arrive mid-conversation via tool results. — Source: [Tracing — OpenAI Agents SDK](https://openai.github.io/openai-agents-python/tracing) (OpenAI — guardrail spans emitted per turn); [Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) (OpenAI) — Check: guardrail middleware runs inside the per-step loop, not only at session start; a test injecting malicious content at turn 3 triggers the same guardrail as turn 1 — Verified: 2026-10-01
- **BU-14** Extract untrusted free text into structured, schema-validated fields (enums, fixed JSON) at every trust boundary so injected natural-language instructions cannot flow unchecked into the next agent or tool call. — Source: [Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety) (OpenAI — "defining structured outputs between nodes... eliminate freeform channels that attackers can exploit") — Check: every handoff/tool-call boundary consuming externally sourced text validates it against a JSON schema before use; raw strings never pass directly as another tool's privileged argument — Verified: 2026-10-01
- **BU-15** Escalate to a human whenever an agent exceeds a configured consecutive-failure threshold on the same subtask, rather than looping indefinitely or silently giving up. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI — "Exceeding failure thresholds... escalate to human intervention") — Check: the run executor tracks consecutive-failure count per subtask and transitions to an `awaiting_human` state past a configured threshold, verified by a test forcing repeated tool failures — Verified: 2026-10-01
- **BU-16** Treat prompts/system instructions as versioned, diffable artifacts stored with IDs, not inline strings scattered across the codebase. — Source: [AWS Well-Architected Generative AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens/generative-ai-lens.html) (AWS — Reliability pillar: "version artifacts"; lifecycle guidance on prompt catalogs) — Check: prompts live in a table/files with a version column and changelog; every run logs the `prompt_version` used, for reproducibility — Verified: 2026-10-01
- **BU-17** Feed tool-call failures back into the agent's context so it can adapt (retry differently, pick another tool), combined with deterministic retry-with-backoff and checkpoints — don't only hard-fail the run. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — "combine the adaptability of AI agents... with deterministic safeguards like retry logic and regular checkpoints") — Check: the tool-call wrapper catches exceptions, writes a structured error back into message history, and only escalates to a hard failure after N retries with backoff — Verified: 2026-10-01
- **BU-18** Use a single prompt template with policy variables per agent role instead of maintaining many near-duplicate system prompts for similar use cases. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI — "use a single flexible base prompt that accepts policy variables") — Check: the repo has one parameterized base prompt per agent role, not N hand-copied prompt variants for N similar use cases — Verified: 2026-10-01
- **BU-19** Before generating code for an ambiguous part of the spec, state assumptions explicitly and surface multiple interpretations instead of silently picking one. — Source: [andrej-karpathy-skills CLAUDE.md](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md) (Karpathy-derived guidelines) — Check: the build-phase generator output includes an explicit "Assumptions" section whenever the architecture spec leaves a field ambiguous — Verified: 2026-10-01
- **BU-20** Generate the minimum code that satisfies the spec: no speculative abstractions, unrequested configurability, or error handling for scenarios the spec doesn't describe. — Source: [andrej-karpathy-skills CLAUDE.md](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md) (Karpathy-derived guidelines) — Check: code review flags any abstraction/interface with a single call site, and any config flag not referenced by the spec — Verified: 2026-10-01
- **BU-21** When editing already-generated code, make surgical, scoped changes — don't "improve" unrelated files or formatting while implementing a requested feature. — Source: [andrej-karpathy-skills CLAUDE.md](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md) (Karpathy-derived guidelines) — Check: the diff for any build-phase edit touches only files/lines traceable to the specific request; unrelated reformatting in the same diff fails review — Verified: 2026-10-01
- **BU-22** Convert every build task into a verifiable goal (a failing test or reproducible repro case) before writing the implementation, and loop until that check passes. — Source: [andrej-karpathy-skills CLAUDE.md](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md) (Karpathy-derived guidelines) — Check: the build workflow requires a test/assertion to exist and fail before the implementation commit, and pass after it — Verified: 2026-10-01

## evals

- **EV-01** Start evaluating with a small set (~20) of real, representative test cases immediately rather than waiting to build a large eval suite; early prompt/tool changes have large, easily detectable effects. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — "Start evaluating immediately with small samples") — Check: the repo has an `evals/` directory with ≥15-20 real-world-derived cases before any production prompt change is merged — Verified: 2026-10-01
- **EV-02** Prefer deterministic, programmatic graders (exact match, schema validation, regex, code execution) over LLM-as-judge wherever a verifiable ground truth exists; reserve LLM-as-judge for free-form outputs without a single correct answer. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — "verifier can be as simple as an exact string comparison... or Claude to judge the response") — Check: the eval harness tags each test case with a grader type (`deterministic`/`llm_judge`), and deterministic graders are used whenever a checkable ground-truth answer exists — Verified: 2026-10-01
- **EV-03** When using LLM-as-judge, score against an explicit multi-criteria rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) with numeric per-dimension scores, not a free-form "is this good?" prompt. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — rubric criteria and "single LLM call... outputting scores 0.0-1.0... most consistent") — Check: the LLM-judge prompt template enumerates named rubric dimensions and outputs a structured per-dimension score object, not one unstructured verdict — Verified: 2026-10-01
- **EV-04** Evaluate stateful/multi-turn agents by end-state outcome (did it reach the correct final state), not by requiring an exact step-by-step match, since valid agents can take different paths. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — "End-state evaluation of agents that mutate state") — Check: eval assertions check final persisted state/output against the expected state rather than an exact tool-call sequence, unless the task explicitly requires a specific process — Verified: 2026-10-01
- **EV-05** Supplement automated evals with recurring manual human review of transcripts — humans catch edge cases (source-selection bias, subtle hallucinations) automated graders miss. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — "Human evaluation catches what automation misses") — Check: the process doc/CI schedule includes a recurring manual transcript-review step with a place to log newly discovered failure modes — Verified: 2026-10-01
- **EV-06** Build tool-level evaluations with realistic multi-tool-call tasks (not toy one-liners) paired with a verifiable outcome, and measure tool-call count, token usage, and error rate, not just final-answer correctness. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: the tool eval suite tracks per-task tool-call count, tokens, and errors in addition to pass/fail, and includes tasks requiring multiple chained tool calls — Verified: 2026-10-01
- **EV-07** Track both pass@k (succeeds at least once in k attempts) and strict run-to-run consistency (succeeds in every one of k attempts) for the same task — high pass@1 with low repeat-consistency means the agent is not safe for unattended production use. — Source: [Evaluating Large Language Models Trained on Code](https://arxiv.org/abs/2107.03374) (OpenAI — original pass@k formulation); [Beyond pass@1: A Reliability Science Framework for Long-Horizon LLM Agents](https://arxiv.org/html/2603.29231v1) (academic, extending τ-bench's pass^k consistency metric) — Check: CI eval runs each high-risk test case k≥3 times and reports both "succeeded at least once" and "succeeded every time" rates, gating merges on a minimum consistency threshold for high-risk task categories — Verified: 2026-10-01
- **EV-08** Run the full eval suite in CI on every prompt, tool-schema, or model-version change, and block merges on eval-score regressions versus the last known-good baseline. — Source: [AWS Well-Architected Generative AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens/generative-ai-lens.html) (AWS — Operational Excellence pillar: "achieve consistent model output quality, monitor and manage operational health") — Check: the CI pipeline runs the eval suite on every PR touching prompts/tools/model config and fails the build if the aggregate score drops below baseline minus an agreed tolerance — Verified: 2026-10-01
- **EV-09** Hold out a separate test set from the examples used to iteratively tune prompts/tools, to detect overfitting to the "training" eval set. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic — "We relied on held-out test sets to ensure we did not overfit to our training evaluations") — Check: the eval directory structure separates `train`/`dev` cases used for iteration from a `holdout`/`test` set run only before release, with no overlap — Verified: 2026-10-01
- **EV-10** Validate a cheaper/alternate model against the full eval suite side-by-side with the strong baseline before promoting it; cost optimization is a post-eval check, not a default starting point. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI — model-selection guidance); [AWS Well-Architected Generative AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens/generative-ai-lens.html) (AWS — Cost Optimization pillar: "select cost-optimized models, balance cost and performance of inference") — Check: any model downgrade/swap PR includes the eval-suite score for both old and new model side by side, and is blocked if the cheaper model regresses below the agreed threshold — Verified: 2026-10-01
- **EV-11** Grade and log traces at the span level (which decision, which tool call, which reasoning step), not only the final output, so regressions can be localized to a specific step. — Source: [Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety) (OpenAI — "Trace grading provides scores and annotations to specific parts of an agent's trace") — Check: the eval/observability pipeline can attach a pass/fail or score annotation to an individual span (tool_call, generation) inside a trace, independently of the run's overall verdict — Verified: 2026-10-01

## ui

- **UI-01** Stream intermediate agent state (plan, in-progress tool calls, partial text) to the UI in real time rather than showing only a spinner until the final answer. — Source: [Loop Control — AI SDK](https://ai-sdk.dev/docs/agents/loop-control) (Vercel — `onStepFinish`/step-streaming) — Check: the UI subscribes to the run's step/stream events and renders at minimum tool-call-in-progress and partial-text states, not just a boolean loading flag — Verified: 2026-10-01
- **UI-02** Surface every tool call made during a run (name, arguments, result summary) in the conversation UI, not only in logs. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic — "Prioritize transparency by explicitly showing the agent's planning steps"); [Tracing — OpenAI Agents SDK](https://openai.github.io/openai-agents-python/tracing) (OpenAI — FunctionSpan captures name/args/result) — Check: the chat UI renders a distinct, expandable tool-call component for every tool invocation in the run, sourced from the same trace data stored in Postgres (AR-15) — Verified: 2026-10-01
- **UI-03** Build a dedicated approval UI (approve/reject with a reason field) for human-in-the-loop gates that visibly blocks the run until a decision is made, not a generic alert/toast. — Source: [Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) (OpenAI — approval interruptions pause the run and resume from state) — Check: the UI has a dedicated pending-approval view listing the exact proposed tool call/arguments, with approve/reject actions that call the resume-run API and persist the decision — Verified: 2026-10-01
- **UI-04** Give the user a visible stop/cancel control for a running agent, and ensure cancellation actually halts further tool calls rather than only hiding the UI. — Source: [AWS Well-Architected Generative AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens/generative-ai-lens.html) (AWS — Reliability pillar: "handle failures gracefully"); [12-Factor Agents](https://github.com/humanlayer/12-factor-agents) (humanlayer — launch/pause/resume with simple APIs) — Check: the UI exposes a stop/cancel control wired to a backend run-cancellation endpoint, and a test confirms no further tool calls execute after cancellation is acknowledged — Verified: 2026-10-01
- **UI-05** Display live run cost/usage (tokens, elapsed tool calls, step count so far vs. configured max) so users see budget consumption for long-running agents. — Source: [AWS Well-Architected Generative AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens/generative-ai-lens.html) (AWS — Cost Optimization pillar: token/cost tracking) — Check: the UI run-detail view shows live step count vs `max_steps` and cumulative token usage sourced from the same metrics captured in tracing (AR-15) — Verified: 2026-10-01
- **UI-06** Render agent-cited sources/evidence inline and visually distinct from the agent's own generated text, so users can verify claims against retrieved content. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — rubric criterion "citation accuracy: do the cited sources match the claims?") — Check: the UI renders citations as distinct linked elements separate from prose, traceable back to the EV-03 citation-accuracy rubric score for that run — Verified: 2026-10-01
- **UI-07** Default long-running agent runs to an async/notify pattern (user can navigate away and is notified on completion or when approval is needed) instead of requiring the tab to stay open and block. — Source: [12-Factor Agents](https://github.com/humanlayer/12-factor-agents) (humanlayer — "trigger from anywhere, meet users where they are") — Check: run state persists server-side (Postgres) independent of an open connection, and a notification/polling mechanism informs the user of completion or pending approval after navigating away — Verified: 2026-10-01
