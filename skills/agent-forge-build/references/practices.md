# Practices — build

Format and upkeep: [practices index](../../agent-forge/references/practices-index.md).

- **BU-01** Implement a minimal, readable agent loop before adopting a heavy framework; if a framework is used, the team must be able to explain what it does under the hood. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: a reviewer can trace the run loop end-to-end in the codebase (or the AI SDK `ToolLoopAgent`) without opening framework internals — Verified: 2026-10-01
- **BU-02** Build fewer, more consolidated tools instead of thin 1:1 wrappers around every API endpoint; combine multi-step operations agents commonly chain into one tool. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: no two tools exist whose descriptions differ only by which of several chained API calls they wrap; tool count tracks distinct user intents, not raw API surface — Verified: 2026-10-01
- **BU-03** Name tool parameters unambiguously (`user_id` not `user`) and give every tool a singular, non-overlapping purpose. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: a schema linter flags generic parameter names (`id`, `data`, `value`) lacking a type-qualifying prefix, and flags tool-description pairs with high textual overlap — Verified: 2026-10-01
- **BU-04** Return token-efficient, high-signal tool responses: paginate/filter/truncate large outputs with sensible default caps, and expose human-readable fields (`name`, not only raw UUIDs). — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic — Claude Code's 25k-token default cap) — Check: every tool response enforces a max-length/token cap in code, and every returned object exposes a human-readable label alongside any machine ID — Verified: 2026-10-01
- **BU-05** Make tool error messages actionable and specific (what went wrong, what to change) instead of opaque error codes or raw tracebacks. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: tool error schema requires a human-readable corrective `message`; raw stack traces are never the primary error payload — Verified: 2026-10-01
- **BU-06** Expose a `response_format` (concise/detailed) verbosity control on data-heavy tools so the agent can request a summary or full detail as needed. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: any tool returning more than ~500 tokens by default exposes a verbosity parameter with a concise default — Verified: 2026-10-01
- **BU-07** Use just-in-time retrieval (query/search on demand) for large or stale data instead of dumping full datasets into the system prompt; load upfront only small, stable, universally-needed context. — Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (Anthropic) — Check: any data source above a size threshold (e.g. >2k tokens) is fetched via a retrieval tool call at run time, never concatenated into the static system prompt — Verified: 2026-10-01
- **BU-08** Implement context compaction for long-running agents: summarize completed work phases into external memory (DB/files) before continuing, and retrieve that memory instead of carrying full history forever. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — "long-horizon conversation management") — Check: the run executor triggers compaction past a token-count threshold, writing a summary record and pruning older messages, verified by a test that exceeds the threshold — Verified: 2026-10-01
- **BU-09** Pass untrusted external content (web pages, emails, tool outputs, uploads) through user-role messages inside a clearly delimited/tagged block; never splice it into system/developer instructions. — Source: [Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety) (OpenAI — "developer messages take precedence... pass untrusted inputs through user messages"); [Defending Against Indirect Prompt Injection Attacks With Spotlighting](https://arxiv.org/abs/2403.14720) (Microsoft Research — datamarking/delimiting) — Check: codebase has one designated injection point wrapping untrusted content in a consistent delimiter/tag (e.g. `<untrusted_data>`), and no raw string-concat of fetched content into the system-prompt builder — Verified: 2026-10-01
- **BU-10** Apply least-privilege scoping to every tool/credential; no tool should have broader read/write/delete access than its specific task requires, and agents that ingest untrusted data should not simultaneously hold high-privilege write tools. — Source: [Taxonomy of Failure Modes in Agentic AI Systems v2.0](https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/final/en-us/microsoft-brand/documents/Taxonomy-of-Failure-Mode-in-Agentic-AI-Systems-Whitepaper.pdf) (Microsoft — "excessive agency", "incorrect permissions"); [AWS Well-Architected Generative AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens/generative-ai-lens.html) (AWS — Security pillar: "mitigate risks of harmful outputs and excessive agency") — Check: a permission audit confirms each tool's credentials are scoped to the minimum resource it touches; any tool that both reads untrusted content and can write/delete is flagged for review — Verified: 2026-10-01
- **BU-11** Require explicit human approval before executing high-risk tool calls (irreversible, financial, destructive), implemented as a pause-and-resume step that halts execution until a decision is recorded. — Source: [Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) (OpenAI) — Check: every tool tagged high-risk in GR-02's risk registry has a matching approval gate that halts the run and persists resumable state until approved/rejected — Verified: 2026-10-01
- **BU-12** Implement guardrails as layered, independent checks (deterministic rules/regex + model-based classifier + moderation) instead of relying on a single LLM call to self-police input and output. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI — "layered defense mechanism... combine LLM-based guardrails, rules-based guardrails... and the moderation API") — Check: the guardrail pipeline has at least 2 independently implemented check types (one deterministic, one model-based) gating both input and output — Verified: 2026-10-01
- **BU-13** Run guardrails on every turn of a multi-turn run, not only on the first user message, since malicious content can arrive mid-conversation via tool results. — Source: [Tracing — OpenAI Agents SDK](https://openai.github.io/openai-agents-python/tracing) (OpenAI — guardrail spans emitted per turn); [Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) (OpenAI) — Check: guardrail middleware runs inside the per-step loop, not only at session start; a test injecting malicious content at turn 3 triggers the same guardrail as turn 1 — Verified: 2026-10-01
- **BU-14** Extract untrusted free text into structured, schema-validated fields (enums, fixed JSON) at every trust boundary so injected natural-language instructions cannot flow unchecked into the next agent or tool call. — Source: [Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety) (OpenAI — "defining structured outputs between nodes... eliminate freeform channels that attackers can exploit") — Check: every handoff/tool-call boundary consuming externally sourced text validates it against a JSON schema before use; raw strings never pass directly as another tool's privileged argument — Verified: 2026-10-01
- **BU-15** Escalate to a human whenever an agent exceeds a configured consecutive-failure threshold on the same subtask, rather than looping indefinitely or silently giving up. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI — "Exceeding failure thresholds... escalate to human intervention") — Check: the run executor tracks consecutive-failure count per subtask and transitions to an `awaiting_human` state past a configured threshold, verified by a test forcing repeated tool failures — Verified: 2026-10-01
- **BU-16** Treat prompts/system instructions as versioned, diffable artifacts stored with IDs, not inline strings scattered across the codebase. — Source: [AWS Well-Architected Generative AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens/generative-ai-lens.html) (AWS — Reliability pillar: "version artifacts"; lifecycle guidance on prompt catalogs) — Check: prompts live in a table/files with a version column and changelog; every run logs the `prompt_version` used, for reproducibility — Verified: 2026-10-01
- **BU-17** Feed tool-call failures back into the agent's context so it can adapt (retry differently, pick another tool), combined with deterministic retry-with-backoff and checkpoints — don't only hard-fail the run. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — "combine the adaptability of AI agents... with deterministic safeguards like retry logic and regular checkpoints") — Check: the tool-call wrapper catches exceptions, writes a structured error back into message history, and only escalates to a hard failure after N retries with backoff — Verified: 2026-10-01
- **BU-18** Use a single prompt template with policy variables per agent role instead of maintaining many near-duplicate system prompts for similar use cases. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI — "use a single flexible base prompt that accepts policy variables") — Check: the repo has one parameterized base prompt per agent role, not N hand-copied prompt variants for N similar use cases — Verified: 2026-10-01
- **BU-19** Before generating code for an ambiguous part of the spec, state assumptions explicitly and surface multiple interpretations instead of silently picking one. — Source: [andrej-karpathy-skills CLAUDE.md](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md) (Karpathy-derived guidelines) — Check: the build-phase generator output includes an explicit "Assumptions" section whenever the architecture spec leaves a field ambiguous — Verified: 2026-10-01
- **BU-20** Generate the minimum code that satisfies the spec: no speculative abstractions, unrequested configurability, or error handling for scenarios the spec doesn't describe. — Source: [andrej-karpathy-skills CLAUDE.md](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md) (Karpathy-derived guidelines) — Check: code review flags any abstraction/interface with a single call site, and any config flag not referenced by the spec — Verified: 2026-10-01
- **BU-21** When editing already-generated code, make surgical, scoped changes — don't "improve" unrelated files or formatting while implementing a requested feature. — Source: [andrej-karpathy-skills CLAUDE.md](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md) (Karpathy-derived guidelines) — Check: the diff for any build-phase edit touches only files/lines traceable to the specific request; unrelated reformatting in the same diff fails review — Verified: 2026-10-01
- **BU-22** Convert every build task into a verifiable goal (a failing test or reproducible repro case) before writing the implementation, and loop until that check passes. — Source: [andrej-karpathy-skills CLAUDE.md](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md) (Karpathy-derived guidelines) — Check: the build workflow requires a test/assertion to exist and fail before the implementation commit, and pass after it — Verified: 2026-10-01
