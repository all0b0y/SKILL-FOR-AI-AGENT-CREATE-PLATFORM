# Practices — architect

Format and upkeep: [practices index](../../agent-forge/references/practices-index.md).

- **AR-01** Place the design on the complexity ladder — single augmented LLM call → prompt chaining → routing → parallelization → orchestrator-workers → evaluator-optimizer → autonomous agent — and justify skipping any lower rung. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: architecture doc maps the chosen pattern to this ladder with a one-line reason for not using the simpler rung below it — Verified: 2026-10-01
- **AR-02** Use predefined-code-path workflows for well-defined, repeatable tasks; reserve open-ended autonomous agents for tasks whose steps can't be predicted in advance. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: each capability in the architecture is tagged `workflow` or `agent` with a justification referencing step predictability — Verified: 2026-10-01
- **AR-03** Choose the orchestrator-workers pattern only when subtasks cannot be pre-defined (unlike static parallelization/sectioning); otherwise use fixed parallelization. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: if orchestrator-workers is chosen, the doc explains why a fixed subtask list (parallelization) was insufficient — Verified: 2026-10-01
- **AR-04** Budget for roughly 4x the token usage of a single chat turn for a single agent, and roughly 15x for a multi-agent system, and require the task's value to justify that multiplier. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic) — Check: cost model includes explicit multiplier fields (chat=1x, agent≈4x, multi-agent≈15x) with a stated dollar budget per task class — Verified: 2026-10-01
- **AR-05** Prefer the centralized "agent-as-tool" pattern (orchestrator stays in control, calls specialists as tools) over decentralized "handoff" (agent permanently transfers control) unless the use case genuinely needs decentralized ownership. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: architecture doc states handoff vs agent-as-tool per multi-agent boundary with the reason for that choice — Verified: 2026-10-01
- **AR-06** Split a single agent into multiple agents only after evals show it fails to follow complex instructions or consistently selects the wrong tool — not preemptively. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: any multi-agent split cites a specific eval failure mode (instruction-following failure or tool mis-selection rate) that justified it — Verified: 2026-10-01
- **AR-07** Give every agent/subagent a single, narrow responsibility; an agent whose prompt covers multiple unrelated domains should be split so each agent produces focused, non-generic output. — Source: [Multi-Agent Portfolio Collaboration with OpenAI Agents SDK](https://developers.openai.com/cookbook/examples/agents_sdk/multi-agent-portfolio-collaboration/multi_agent_portfolio_collaboration/) (OpenAI) — Check: each agent's system prompt/spec entry maps to exactly one named responsibility in the architecture doc; multi-domain prompts are flagged for splitting — Verified: 2026-10-01
- **AR-08** Give each agent its own narrowly scoped toolset; never share a tool across agents operating in different trust/data-sensitivity domains. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: tool-assignment matrix shows no tool shared across agents flagged with different data-sensitivity domains — Verified: 2026-10-01
- **AR-09** Decide explicitly whether subagents execute synchronously (lead blocks until completion) or asynchronously, and document the resulting bottleneck/coordination tradeoff rather than assuming free concurrency. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic) — Check: architecture doc states the sync/async execution model for subagents and the known tradeoff it accepts — Verified: 2026-10-01
- **AR-10** Namespace tools by service and resource (`<service>_<resource>_<verb>`) whenever tools from more than one service or MCP server share the agent, to prevent confusion between overlapping tools. — Source: [Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (Anthropic) — Check: `check-tools` rejects an unprefixed tool name when the registry holds tools from more than one service/MCP server — Verified: 2026-10-01
- **AR-11** Route easy/common queries to small, cheap models and hard/unusual queries to frontier models per-step, rather than hardcoding one model for the whole system. — Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic) — Check: architecture/config has a per-agent or per-route model field, not a single global model constant — Verified: 2026-10-01
- **AR-12** Persist full agent run state (messages, step index, tool results) in Postgres from day one so a crashed worker resumes mid-run instead of restarting from step 0. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic); [12-Factor Agents](https://github.com/humanlayer/12-factor-agents) (humanlayer) — Check: a `runs`/`run_steps` table stores enough state to resume; an integration test kills the worker mid-run and asserts it resumes from the last completed step, not the start — Verified: 2026-10-01
- **AR-13** Model each run step as a stateless reducer — `(prior_state, event) -> (new_state, next_action)` — so runs can be paused, serialized, and resumed by any process. — Source: [12-Factor Agents](https://github.com/humanlayer/12-factor-agents) (humanlayer) — Check: the run executor keeps no in-memory-only state that is not also written to persisted run state after every step — Verified: 2026-10-01
- **AR-14** Design every side-effecting tool/action handler to be idempotent via an idempotency key per run-step, since durable execution and model retries will replay steps. — Source: [12-Factor Agents](https://github.com/humanlayer/12-factor-agents) (humanlayer); [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic — retry logic and checkpoints) — Check: every side-effecting tool call is keyed by `(run_id, step_id)`, and replaying the same key short-circuits instead of double-executing (covered by an automated test) — Verified: 2026-10-01
- **AR-15** Plan OpenTelemetry-style span tracing (agent, generation, tool-call, handoff, guardrail spans) stored durably in Postgres, not only in an external vendor dashboard. — Source: [Tracing — OpenAI Agents SDK](https://openai.github.io/openai-agents-python/tracing) (OpenAI) — Check: trace schema has distinct span types for agent/generation/tool/handoff/guardrail with `parent_id` links forming a tree per `run_id` — Verified: 2026-10-01
- **AR-16** Make maximum-turn / maximum-tool-call a required, finite run parameter at architecture time — "reaching a maximum number of turns" must be a designed exit condition, not an afterthought. — Source: [A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (OpenAI) — Check: run-config schema requires a finite `max_steps`/`max_turns` integer; no "unlimited" value is accepted in production config validation — Verified: 2026-10-01
- **AR-17** Run agent work through a durable queue (claim/lock with persisted status) rather than an in-memory/ephemeral one, so runs survive process restarts and deploys. (agent-forge implements this with pg-boss on Postgres — a stack decision, not part of the cited source.) — Source: [AWS Well-Architected Generative AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/generative-ai-lens/generative-ai-lens.html) (AWS — Reliability pillar: "handle failures gracefully... version artifacts... verify completion of distributed computation tasks") — Check: queue table has a `status` enum and a row-claim mechanism verified not to double-process a row under concurrent workers — Verified: 2026-10-01
- **AR-18** Plan rolling/rainbow worker deployments so in-flight agent runs on the old code version are drained, not hard-killed, by a deploy. — Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (Anthropic) — Check: deploy pipeline keeps the old worker version draining in-flight runs for a grace period instead of terminating it on deploy — Verified: 2026-10-01
